# Group 10 workflow release

This branch changes experimental roles and reporting from Group 10. It does **not** change production GP architecture, scaling, noise, source transfer, acquisition or the modeled mechanical endpoint. Retraining on newly measured observations continues normally. Reference-role observations are excluded from production training.

## Activation and historical boundary

`config_v2/group10.yaml` contains the workflow activation round (10), locked false production-revision flags, reference replicate count and supplementary detector settings. Application requirements live only in `config_v2/endpoints.yaml`. Each new proposal freezes the effective configuration and training evidence hash. Group 9 and all earlier proposal bytes remain unchanged. Existing observation/worksheet columns remain supported.

No live Group 10 proposal was generated by this implementation. The demonstration is isolated and based on the Group 8 snapshot, with synthetic Group 10 outcomes. It is not a recommended experimental slate after Group 9.

At Group 9 completion, use the existing `--skip-generate` Stage 3 option if the Group 10 policy/settings are not ready. Generate Group 10 only after incorporating the actual Group 9 observations and reviewing readiness. Do not rerun database initialization.

## Screened hits and reference

The new selector reserves existing measured intact-passing formulations for first mechanical characterization. Stable formulation IDs are retained; new candidate IDs identify the new experiments. Rank hits by all-batch observed mean viability, lower between-batch SD, then formulation ID. Historical pass/fail disagreement is retained in explanations. Retests remain distinct. Ordinary novelty, ingredient frequency, pair/combination, boundary, and cold-ingredient caps remain enforced. Residual origin quotas use the existing slate's ordinary-origin proportions after reserving special and rescue rows; unsatisfied quotas fail before proposal writes.

Without a ready reference: two screened hits plus two fresh mechanical candidates. With the reference: one reference, one screened hit and two fresh candidates. Existing bootstrap diversity ordering is used for fresh rows; existing hybrid/full acquisition ordering is retained for those phases. Follow-up/control rows have intentional repeat exceptions. Actual intact failure promotes ordered backups. Every followed-up formulation must have fresh viability and intact results in the mechanical batch.

The reference is exactly **2.5% v/v DMSO + 100 mM sucrose** in final volume. Its DMSO conversion is `25 mL/L × density × purity / 78.13 g/mol`. Density is now set to the literature value 1.10 g/mL and purity to the user-specified 100%; only its ordinary test replicate count remains pending before it becomes ready. All formulations share the same base medium and replicates come from one preparation. Until then the metadata lists missing fields and no reference slot is reserved. The narrow exception changes only this recipe's DMSO ceiling; other feasibility/availability checks still apply. The normal 0.10 M DMSO candidate ceiling does not change.

Reference results are stored with `experimental_role=campaign_control`, excluded from GP training and primary prospective prediction eligibility, and reported separately. No normalization is performed. It is a designated reference, not an established stable anchor. Sucrose is an existing feature.

The separate confirmation feature has been removed at user request. There are no confirmation reservations, cadence settings, or independent-batch requirements. Existing viability retests and screened-hit first-mechanics follow-up remain.

## Entry fields and workload

New worksheets add preparation, specimen, readout, cell-batch and protocol IDs; mechanical test ID/attempt flag; definition/hash metadata; supplementary analysis path; and the frozen experimental role. The operator edits result/protocol fields only, not roles, composition or ranks.

Four mechanical slots mean four formulations. Use distinct mechanical test IDs for compression replicates. Replicates share one formulation preparation; preparation IDs remain optional provenance and are not required setup inputs. The execution manifest reports formulation allocation/attempt counts, identified specimen runs (or unknown if IDs are absent), interpretable legacy-result rows, and usable formulation-level observations. An attempted test with no usable outcome still consumes its formulation allocation.

## Acceptance reports

Thresholds default to null. Zero is a real threshold. Reports separate pending/partial requirements, missing or incompatible measurements, below-threshold results and measured threshold passes. Intact formation is required. Paired means belong to the same formulation/batch. The supplementary definition is `supported_load_1mm_v1`; the existing endpoint is labeled `legacy_curve_maximum_v1` in acceptance reporting. Enter the exact definition ID in the requirements entry. No acceptance threshold changes acquisition or the hypervolume reference. Acceptance stops at measured requirements met; there is no confirmation classification.

## Architecture and ownership

- `group10_config.py`: settings validation, readiness and production-evidence exclusions.
- `group10_selection.py`: forward-only typed reservations and constrained slate assembly, called from the Stage 2 workflow.
- `mechanical_events.py`: pure supplementary detector and explicit-output plotting; `analyze_mechanical.py` is its CLI.
- `feedback.py` and `mechanics_execution.py`: compatible ingestion and attempt accounting.
- `acceptance.py`, `group10_reporting.py`: derived application/control/cohort reports.
- `observation_noise.py`, `batch_effects.py`, `audit_models.py`, `audit_acquisition.py`: offline-only estimates/models; no production selector imports these audit models.
- `audit_group10.py`: required-output forward replay and decision report.

See `settings_register.md`, `mechanical_sop.md`, `audit/audit_report.md`, and `verification.md` for pending values, protocol semantics, comparative evidence and test status.

## Model transition timing

Any approved model/endpoint switch belongs at the beginning of full mechanics: review the audit, choose the configuration, and freeze it before the first full-mechanics proposal. No automatic switch is enabled and no model is selected by this timing setting.
